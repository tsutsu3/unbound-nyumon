同じ名前を続けて問い合わせると、2回目は外部の DNS サーバーへ問い合わせずに応答できることがあります。なぜでしょうか。この章では、その仕組みを追いながら DNS キャッシュの働きを見ていきます。

## 1回目 - ルートから委任をたどる

フルリゾルバーが `www.example.com` の A を初めて聞かれたとき、手元には何もありません。この状態を **キャッシュミス**（cache miss）と呼びます。

フルリゾルバーは、あらかじめ持っているルート DNS サーバーのアドレスから始め、委任を1段ずつたどります。

1. ルート DNS サーバーへ問い合わせる ➡ `com` の権威 DNS サーバーを示す委任応答が返る
2. `com` の権威 DNS サーバーへ問い合わせる ➡ `example.com` の権威 DNS サーバーを示す委任応答が返る
3. `example.com` の権威 DNS サーバーへ問い合わせる ➡ `www.example.com` の A が返る

途中の2回で返るのは委任応答、つまり次に聞く先の案内です。ルート DNS サーバーも `com` の権威 DNS サーバーも、最終的な答えは持っていません。答えを持っているのは、その名前を含むゾーンの権威 DNS サーバーだけです。

この間、依頼したスタブリゾルバーは待っています。スタブリゾルバーが送った問い合わせは1回で、3回の問い合わせを行ったのはフルリゾルバーです。

## キャッシュに入るもの

フルリゾルバーは、得られた情報を捨てずに保存します。保存されるのは最終的な答えだけではありません。途中で得た「`com` の権威 DNS サーバーはどこか」「`example.com` の権威 DNS サーバーはどこか」も保存されます。

そのため、次に `mail.example.com` を聞かれたときは、ルートからやり直さずに `example.com` の権威 DNS サーバーへ直接問い合わせられます。キャッシュが効くのは、同じ名前を2回引いたときだけではありません。

なお、フルリゾルバーが持つキャッシュは1つの入れ物ではありません。Unbound が何をどこに保存しているかは第4章で説明します。

## 2回目 - 何が省かれるか

同じ `www.example.com` をもう一度聞かれたとき、フルリゾルバーは保存した答えをそのまま返します。この状態を **キャッシュヒット**（cache hit）と呼びます。応答は、権威 DNS サーバーへの問い合わせを待たずに返ります。

1回目と2回目で違うのは、次の2点です。

- 応答までの時間: 外部への往復がなくなるぶん短くなります
- 返る TTL: 保存してからの経過時間だけ減った値が返ります

答えの内容そのものは変わりません。

## TTL は誰が決めるのか

**TTL**（Time To Live）は、そのデータを持つ権威 DNS サーバーが付けた値です。フルリゾルバーが決めるものでも、問い合わせた側が指定するものでもありません。

TTL は、その情報をキャッシュしてよい時間の最大値です。短く扱うことは許されており、フルリゾルバーが上限を設けて短く丸めることもあります[^ttl]。逆に、権威 DNS サーバーが付けた TTL を超えて使い続けることは、通常は想定されていません。

TTL を過ぎると、フルリゾルバーは原則としてもう一度権威 DNS サーバーへ問い合わせます。ただし、問い合わせ先に届かないなどの理由で更新できない場合に、期限切れの情報を返す仕組みもあります。Unbound がこれをどう扱うかは第4章で説明します。

## 「名前がない」と「そのレコードがない」

答えが得られない場合にも2種類あります。この区別は、第5章で Unbound に名前を答えさせるときに効いてきます。

- **NXDOMAIN**: その名前自体が存在しません。`example.com` に `nosuchhost` という名前がそもそもない場合がこれにあたります
- **NODATA**: 名前は存在しますが、問い合わせた型のデータがありません。`www.example.com` に A はあるが AAAA はない場合がこれにあたります

どちらも「答えが返らない」点では同じに見えますが、名前が存在しないのか、型のデータがないのかが違います。この2つは DNS の応答としても別物で、応答のどこを見て区別するかは第3章で扱います。

この2種類の結果も、フルリゾルバーはキャッシュします。「ない」という答えを保存しておくことを**ネガティブキャッシュ**（negative cache）と呼び、通常の答えの保存（positive cache）と区別します[^negcache]。ネガティブキャッシュがあるため、存在しない名前を何度引いても、その都度ルートからたどり直すことにはなりません。

ネガティブキャッシュは、問い合わせが失敗したことを覚える仕組みではありません。権威 DNS サーバーが「ない」と答えた、というその答えを保存するものです。保存してよい時間は、そのゾーンの SOA をもとに権威 DNS サーバーが決めます[^soamin]。この関係は第4章で説明します。

## 実際に2回引いて TTL を見る

`dig` で同じ名前を2回引き、TTL が減ることを確認します。見るのは ANSWER セクションだけです。出力全体の読み方は第3章で扱います。

```sh
$ dig example.com A +noall +answer
example.com.		296	IN	A	104.20.23.154
example.com.		296	IN	A	172.66.147.243
```

3秒後に、同じ問い合わせをもう一度送ります。

```sh
$ dig example.com A +noall +answer
example.com.		293	IN	A	172.66.147.243
example.com.		293	IN	A	104.20.23.154
```

返ってきたアドレスは同じで、TTL だけが296から293へ、経過した3秒ぶん減っています。TTL が減っているのは、この答えがキャッシュから返っているからです。

行の順序が1回目と2回目で入れ替わっている点は、ここでは気にしません。この出力は OS に設定された問い合わせ先へ引いた結果であり、アドレスも TTL の絶対値も環境と時刻によって変わります。確認したいのは、2回目の TTL が減っていることだけです。

[^ttl]: [RFC 2181 の 8. Time to Live (TTL)](https://www.rfc-editor.org/rfc/rfc2181#section-8)。TTL は最大値であって、その時間だけ保持することを強制するものではない。

[^negcache]: [RFC 2308 の 5. Caching Negative Answers](https://www.rfc-editor.org/rfc/rfc2308#section-5)

[^soamin]: [RFC 2308 の 4. SOA Minimum Field](https://www.rfc-editor.org/rfc/rfc2308#section-4)
